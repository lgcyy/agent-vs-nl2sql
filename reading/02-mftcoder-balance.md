## 1. 三种平衡分别在处理什么

| 层面 | 想避免的问题 | 原文思路 | 本轮证据判断 |
| --- | --- | --- | --- |
| 数据量 | 数据多／有效 token 多的任务在汇聚时获得更大系数 | 任务内归一化，再对任务汇聚 | §4.1 主比较明确采用 Data-Balance Eq.1 |
| 难度 | 已经容易预测的样本／任务仍占用较多优化份额 | 样本级或任务级 focal，Eq.2／3 | 提出了公式；主表不能单独证明该扩展的增益 |
| 收敛速度 | 一个任务已接近最佳点，另一个尚未学好 | 根据验证损失进展调整任务权重，Eq.4 | §6 承认尝试成本与效果仍不理想；附录 B 是问题曲线，不是该扩展的独立消融 |

三者不是一个已被主表验证的完整叠加配方。难度是当前模型对监督目标的预测状态，收敛速度是这种状态怎样随训练变化；两者也不能混用。[原文 §3.5、§4.1、§6](https://arxiv.org/html/2311.02303v1)

## 2. 难度平衡：少花力气在已经容易的目标上

### 2.1 原文的概率到底是什么

对任务 i 的样本 j，令有效监督位置数为 T_ij，位置 t 上目标 token 的条件概率为 p_ijt。把原文 Eq.2 改写为：

$$
\bar p_{ij}=\frac{1}{T_{ij}}\sum_t p_{ijt},\qquad
\ell_{ij}=-\frac{1}{T_{ij}}\sum_t\log p_{ijt},
$$

$$
L_{\mathrm{sample}}=
\frac{1}{\sum_i M_i}\sum_i\sum_{j=1}^{M_i}
\alpha_i(1-\bar p_{ij})^\gamma\ell_{ij}.
$$

这里的 p 按语言模型交叉熵的含义解释为示范目标 token 的概率；平均概率不等于整段输出正确概率，也不等于工具调用成功率。α_i 是式中的任务系数，γ 控制调制强度。任务级 Eq.3 则先对同任务的样本均值再平均，形成该任务的平均概率与损失，再加 focal 因子。[v1 Eq.2／3](https://arxiv.org/html/2311.02303v1#S3.SS5)

**本仓库教学例子：**令 α_i=1、γ=2；一个样本的平均目标概率为 0.9，另一个为 0.5，则调制因子分别是 0.01 和 0.25。后者获得 25 倍的乘法因子。它说明“容易的目标被相对减弱”，不表示实际梯度范数就是 25 倍，更不是 Agent 比 SQL 难 25 倍。

### 2.2 为什么需要谨慎解释“难”

这是我们的分析：一个示范 token 概率低，可能因为需要学习新能力，也可能因为措辞有多个等价选择、格式少见、示范有噪声。只凭这一数值不能判断增加监督权重的业务价值。

平均概率还可能掩盖少数关键位置。设一个人工构造的 100-token 目标中，99 个位置的目标概率为 0.99，仅一个决定下一步动作的位置为 0.01；其平均值仍为 0.9802，γ=2 的因子约为 0.000392。这个例子只说明平均量的局限，**不是把概率 0.01 当作确定动作失败**，也不是对实际 Agent 数据的测量。若业务结果高度依赖少量决策，序列平均难度就未必表达其重要程度。

还有两个容易丢失的数学细节：

- Eq.2 以样本均值汇聚，Eq.3 在任务内也先平均样本；Eq.1 在任务内按有效 token 平均。因此，即使 γ=0，长度不等时也不能一概说“退回 Eq.1”。
- 若 focal 因子随 θ 变化且未停止梯度，求导包含额外项：∇(wℓ)=w∇ℓ+ℓ∇w。v1 没有明确给出 stop-gradient 规则。固定代码的 `loss_func_mft` 也不包含 Eq.2／3 的 focal 分支，故本轮不能认证其实际自动微分行为。不能借后来 CoBa 的 no_grad 路径倒推原始 focal。

上述公式核读自 v1；代码范围仅限已读的 [accelerate loss 函数](https://github.com/codefuse-ai/MFTCoder/blob/8ba13f44e2036f1412a343bc343dc6cda7383d73/mftcoder_accelerate/src/utils/loss_utils.py)，不声称整个项目从未出现过 focal 实现。

## 3. 收敛平衡：同一时刻，两个任务可能处在不同学习阶段

### 3.1 当前 loss 大小和学习速度是两件事

**以下为自造验证损失，不是论文或业务观测：**

| 训练位置 | SQL 验证 loss | Agent 验证 loss |
| --- | ---: | ---: |
| t0 | 1.00 | 2.00 |
| t1 | 0.65 | 1.60 |
| t2 | 0.60 | 1.30 |
| t3 | 0.66 | 1.10 |

SQL 在 t2 最好，之后回升；Agent 还在下降。若继续按照相同规则训练，会出现选早一点更照顾 SQL、选晚一点更照顾 Agent 的矛盾。当前较高的 loss 不自动意味着收敛更慢：上表 t1→t2 的相对下降率约为 SQL 7.7%、Agent 18.75%。而 SQL t2→t3 为 −10%，Agent 约为 15.4%。负的相对下降表示验证损失回升。

便于理解的历史进展指标可以写成：

$$
r_i=\frac{V_i(t-\Delta)-V_i(t)}{V_i(t-\Delta)+\epsilon}.
$$

**这只是教学指标，不是原文 Eq.4 的实现。** 原文讨论的是候选更新方向带来的相对验证损失改善，并借鉴 FAMO 的最慢任务进展目标；不能把上述两点差分伪装成论文完整优化算法。

### 3.2 “下降慢就加权”缺少哪一步

损失几乎不降，至少可能有几种不同情况：已经学得很好；还未得到足够有效学习；遇到噪声或难以学习的目标；其他任务更新抵消了改善。曲线平坦这个观测本身不能区分它们。若验证 loss 开始回升，继续加权同一训练数据也未必能修复泛化。

因此，动态权重有一个实质假设：**观察到的验证进展能够为接下来如何分配训练提供有效反馈。** 它并没有由“loss 有下降速度”自动成立。

v1 §6 报告代码补全与单测生成收敛不同步，并承认其 FAMO 式尝试带来较高训练成本、额外收敛 epoch，而收益不匹配。这里转述的是作者在该文的尝试，不把“两次反传”泛化成原始 FAMO 算法的必然性质。原文 Eq.4 还同时使用 g_t 与未在该段明确解释的 d_t，本讲不据此拼出已验证的完整实现。[v1 §6、附录 B](https://arxiv.org/html/2311.02303v1)

### 3.3 后来 CoBa 属于另一项工作

[CoBa](https://aclanthology.org/2024.emnlp-main.459/) 正式发表于 EMNLP 2024，进一步围绕收敛反馈设计动态任务权重。固定仓库的 [README](https://github.com/codefuse-ai/MFTCoder/blob/8ba13f44e2036f1412a343bc343dc6cda7383d73/README.md) 在 2024-10-31 的发布记录中说明将 self-paced 更新为 CoBa。当前 `CoBaStatus` 使用验证损失历史曲线等信号；它与 v1 的表述及原始主表分开记录，本轮不另开一篇 CoBa 精读。

## 4. 容易忽略的第三个问题：任务标签也在决定权重

**下面是本仓库推导。** 设 SQL 和 Agent 原本各被定义为一个任务，等权目标为：

$$
L=\tfrac12\ell_{\mathrm{SQL}}+\tfrac12\ell_{\mathrm{Agent}}.
$$

现在仅将 SQL 划成五个子组，并假设每组的有效监督 token 总数相等；Agent 仍是一组。数据及监督内容不变，对六个标签等权得到：

$$
L'=\frac16\sum_{j=1}^{5}\ell_{\mathrm{SQL},j}
+\frac16\ell_{\mathrm{Agent}}
=\frac56\ell_{\mathrm{SQL}}+\frac16\ell_{\mathrm{Agent}}.
$$

因此，“任务等权”只有在明确任务划分后才有完整含义。它不是对任意标签组织都保持不变的客观公平原则。这也不说明应该拆成五组；它只是一个反例。这是所写完整等权目标的代数例子，不代表局部 microbatch 实现自动赋予全训练过程 SQL 5/6 的权重。

v1 §6 的经验同样没有支持任意细分：作者报告按难度或编程语言拆分的尝试没有优于 mixed SFT。对我们，SQL／Agent 是业务定义，不能直接等同于内部全部监督成分都同质。[原文讨论](https://arxiv.org/html/2311.02303v1#S6)

## 5. 为什么“平衡”不等于共同改善

为区分数学关系，考虑一次理想化普通梯度更新。任务权重 a 在这一步被视作外部常数，令 g_SQL、g_Agent 为两个固定损失的梯度：

$$
v=a g_{\mathrm{SQL}}+(1-a)g_{\mathrm{Agent}},\qquad
\theta'=\theta-\eta v.
$$

小步长一阶近似下，两任务都改善要求各自与 v 的内积均为正。仅令 a=1/2 并不保证它们成立。

**自造向量例子：**令 g_SQL=(1,0)、g_Agent=(−2,1)。等权时 v=(−0.5,0.5)，SQL 内积为 −0.5，Agent 内积为 1.5，于是 SQL loss 一阶上升、Agent 下降。取 a=0.7 则 v=(0.1,0.3)，两个内积都为 0.1，局部上存在共同改善。这个例子同时说明：等权不是充分条件，负的任务梯度内积也不等于所有加权都无解。

这不是当前模型的梯度观测，也不能证明两个业务评测为何都跌破起点。真实优化器、训练全过程、泛化表现、SQL 执行正确率和 Agent 成功率都不由这一步的一阶近似保证。若使用未 detach 的 focal，前述 v 还不能省略权重自身的导数项。

## 6. 收束：MFTCoder 应保留什么

**主证据：**v1 Table 2 中，MFT 相对普通混训在 HumanEval／MBPP 提高 2.44／2.40 个百分点，相对对应单训提高 0.61／1.80 个百分点。主表明确采用 Eq.1，故不能把这些差值归功于 focal 或动态收敛权重。对应单训参考来自两个模型。[原文主表](https://arxiv.org/html/2311.02303v1#S4.SS3.SSS1)

同表引用的 CodeLlama base 为 43.3%／49.0%，普通混训 57.93%／53.6% 在数值上仍高于它们；base 数值来自 CodeLlama 报告，不能认定是本文同设置重新评估。该主表并未复现我们“两侧都低于共同起点”的严格现象。各模型独立早停、主表未给多次运行误差范围，也要继续保留。结果支持的是这套训练方案的经验效果，不能把全部改善严格归因于一个已单独隔离的 loss 算子。

**我们的定位：**保留它对训练目标、任务划分和学习进展的分层描述。它提供了可读源码和相邻实证，但没有建立本业务双侧回退的因果机制，也没有证明某一种平衡会同时恢复两侧能力。用户可能已经见过或使用类似归一化，本轮没有读取业务实现，不将其列为已发现的修复。

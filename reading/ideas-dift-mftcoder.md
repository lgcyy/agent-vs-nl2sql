## 1. 两个核心 idea

| 维度 | DiFT · ICLR 2026 | MFTCoder · KDD 2024；技术阅读为 arXiv v1 |
| --- | --- | --- |
| 一句话 | 借单训模型寻找任务相关参数行，再限制混训的可更新范围 | 保留任务分组，明确监督如何汇聚，并讨论依据难度与学习进展调整权重 |
| 主要控制对象 | 哪些参数允许被修改 | 哪些监督以多大系数进入训练目标 |
| 主要信号 | 起点与对应单训模型的层输出激活差异 | 任务标签、有效监督量；扩展讨论目标概率与验证损失变化 |
| 混训操作 | 各任务逐层 Top-C 参数行集合取并集，从共同起点在混合数据上更新该并集 | 主比较采用任务内 token 平均、任务间平均；难度／收敛平衡分别另有表述 |
| 关键假设（我们的概括） | 由单训激活变化选中的位置，对联合适配仍有足够价值；限制其他更新能改善结果 | 所定义的任务与监督平均量有意义；改变它们的相对权重能改善联合学习 |
| 没有保证的事 | 并集内部的更新方向相容；无损恢复两个单训能力 | 任务等权、loss 下降或同步收敛会转化为两侧业务指标恢复 |
| 当前处置 | 用户明确暂不喜欢此方法，保留背景，不作为当前优先方案 | 核心阅读已完成；保留为目标函数与实现参考，不宣称已选定业务方法 |

方法依据：[DiFT §4.1–4.2](https://proceedings.iclr.cc/paper_files/paper/2026/file/b304a04c6a4ac168aa692923814ace17-Paper-Conference.pdf)、[MFTCoder v1 §3.5、§4.1](https://arxiv.org/html/2311.02303v1)。假设、价值判断及业务适用性均为本仓库分析。

## 2. DiFT：值得记住的思路与不能越过的边界

### 原始思路

先分别得到任务单训模型；同样输入分别经过共同起点和对应单训模型，按层统计输出激活差的平方量，选每层变化较大的参数行。混训时取各任务集合的**并集，保留交集**，回到共同起点，只更新选中位置。它没有把两个单训模型权重直接合并，也没有在混训中按当前样本切换不同参数集合。[正式原文 §4.1–4.2、Algorithm 1](https://proceedings.iclr.cc/paper_files/paper/2026/file/b304a04c6a4ac168aa692923814ace17-Paper-Conference.pdf)

### 我们认为可借鉴的 idea

单训模型除了提供最终成绩，也可能提供“学习过程中哪些位置发生变化”的分析线索。由此可以将“参数位置是否与任务相关”和“联合更新是否协调”分开讨论。这个分析视角可以保留，不要求接受作者的整个训练方法。

### 关键限制

激活变化包含上游输入变化；平方变化量缺少更新方向信息。位置敏感性不能单独证明某行只承载某能力，也不能证明两个任务在该位置上的目标相容。选并集后，交集仍然共享；统一并集掩码也未阻止一个任务的数据更新另一任务选入的位置。大变化还不自动等于有益变化，尤其不能把单训“可接受”扩写为所有单训变化均有益。

本仓库对主表六组混训配置重算：相对普通混训，**3 组两侧都升、3 组有取舍**；相对对应单训参考，**1 组两侧都升、3 组有取舍、2 组两侧都降**。这些是报告点估计的比较，不是显著性结论或方法成功率；两个单训参考来自不同模型，跨指标同一 checkpoint 的选择仍未核实。[原表与逐项重算](01-dift-evidence.md)、[机器可读记录](../resources/dift-mix-evidence.json)

Mistral 代码＋逻辑是较近的退化例子，但小幅下降、代码指标口径、表内箭头与选点问题均保留。官方附件中已有分析／选择／训练相关源码，完整复现链未核实。不能概括成“没有代码”，也不能概括成“已经可复现且证明双侧恢复”。

**处置：**用户暂不优先考虑此方法。我们保留问题对照、参数位置分析与负面结果；不把个人方法偏好改写成方法已被证明无效。

## 3. MFTCoder：值得记住的思路与不能越过的边界

### 原始思路

多任务数据被拼接后，不同汇聚方式仍对应不同目标。Eq.1 将每个任务的有效监督 token loss 分别平均，再在任务间平均；Eq.2／3 讨论按目标概率调制的 focal；Eq.4 讨论收敛反馈。**§4.1 主比较明确使用 Eq.1**，不能把三项写成主表共同验证的系统。[v1 正文](https://arxiv.org/html/2311.02303v1)

### 我们认为可借鉴的 idea

真正需要描述的是监督进入训练目标的全过程：数据抽取、有效 token、输入行／原记录边界、任务划分与权重、局部及全局汇聚。只说“几比几混合”无法完整说明优化了什么。

难度与收敛反馈还提醒我们，静态数据占比不包含学习状态。但“当前难”“下降慢”“继续训练有益”是三项不同判断，不能用一个 loss 数值互相替代。

### 最强正面证据与限制

v1 Table 2 的 HumanEval／MBPP，MFT 相对普通混训提高 **2.44／2.40 个百分点**，相对对应单训提高 **0.61／1.80 个百分点**。主表基于五类代码任务，不是 SQL＋长程 Agent；Text-to-SQL 只是未见任务迁移评测。base 一行取自 CodeLlama 报告，Mixed 也未低于该行，不能称为本业务严格退化现象的复现。[主表与设置](02-mftcoder.md)、[原始值核查](../resources/mftcoder-reading-evidence.json)

各模型独立早停，累计训练预算未核为完全一致；主表没有多次训练误差范围。结果支持的是该训练方案，不能把全部差值严格归因于一个已经独立隔离的 loss 算子。§6 承认任务拆分、不同收敛速度及共享更新冲突仍是问题；focal 和动态收敛扩展没有由这张主表分别建立增益。

固定源码中还必须保留两个实现边界：任务权重只在当前调用出现的任务之间归一化；packing 后输入张量的一行未必是一条原始轨迹。当前代码包含后续 CoBa，不能反向归因到 v1 主表。[固定 loss](https://github.com/codefuse-ai/MFTCoder/blob/8ba13f44e2036f1412a343bc343dc6cda7383d73/mftcoder_accelerate/src/utils/loss_utils.py)、[后半篇](02-mftcoder-balance.md)

**处置：**保留为实现检查和目标定义的基础参考；本轮没有证据认定用户现有训练缺少这些设计。

## 4. 放在一起看：参数范围与监督权重是两项不同选择

下面是本仓库的概念模型，不是两篇共同提出的算法。考虑普通梯度下降，固定参数掩码 P_S，任务权重 a_k 在本步作为常数：

$$
\Delta\theta=-\eta P_S\!\left(\sum_k a_k\nabla L_k\right).
$$

DiFT 的混训选择主要对应 P_S；MFTCoder 的主要数据平衡选择主要对应 L_k 的定义及 a_k。后者本身也使用 PEFT，这里只是抽出两篇在本次阅读中最相关的差异，不说 MFTCoder 毫无参数约束。

若权重依赖 θ 且不 detach，上式还缺少权重导数；真实 Adam／LoRA 等优化路径也不能被这个示意式完全替代。

由此可提出三个独立问题：

1. **位置：**允许修改的参数是否足以承载联合适配？
2. **方向：**来自不同监督的实际更新能否共同改善相关目标？
3. **行为：**训练或验证 loss 的改善，能否转成 SQL 正确率及 Agent 成功率？

位置相关不是方向协调的充分证据；方向上的局部共同下降不是行为指标恢复的充分证据。这些是数学和测量层面的区分，尚不是当前业务的因果诊断。

## 5. 与我们的严格问题对齐

目前用户确认的事实：共同起点为用户提供名称的 **Qwen-3.8-27B**；NL2SQL-noCoT 与长程 Agent 各自单训可接受；同一个混训 checkpoint 在两侧均低于对应单训，而且两侧均低于共同 SFT 前起点。

据此，后续阅读要逐侧同时保留两条参考线：对应单训与共同起点。单训可接受不扩写成单训都超过起点；noCoT 不等于没有推理，长程交互也不自动等于长 CoT。[完整问题定义](../problem.md)

| 已学到的区分 | 当前仍不能断言 |
| --- | --- |
| 相同样本比例可能对应不同损失系数 | 当前双降就是因为长 Agent 主导训练 |
| 参数选择可改变允许的更新范围 | DiFT 的敏感行等同于独立能力模块 |
| 任务划分会影响等权目标 | SQL／Agent 的最佳划分和权重已知 |
| loss、学习进展与任务成功率不同 | 使两条 loss 曲线同步就能恢复业务能力 |
| 两篇提供相邻实证与可分析方法 | 它们已覆盖本业务，或已足以证明新论文贡献 |

**保留的研究认识：**联合 SFT 中，监督如何定义、参数如何更新、业务行为如何评价，需要同时说清楚。这一认识帮助继续阅读，不是已完成的新方法。下一篇按原名单进入 [DMO](../papers/a-02-data-mixing-optimization.md)，讨论任务权重如何选及其目标边界。
